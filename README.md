# Neno & Zaka

The member-facing half of the church management system. Three tabs:

- **Biblia** — the Swahili Bible, searchable, fully offline
- **Nyimbo** — *Nyimbo za Kristo* hymnal, fully offline
- **Taarifa** — the member's own giving record

Its counterpart is [`../Pastor`](../Pastor), the staff app. They share one
Supabase project and no code — see [`../README.md`](../README.md).

## Running it

```bash
npm install
```

Create `.env.local` from [`.env.example`](.env.example), then:

```bash
npm run dev
```

Serves on **port 3000**. The first run parses `bible.pdf` and
`Nyimbo-Za-Kristo-Kk.txt` into SQLite databases, which takes a while; after that
`public/bible.db` and `public/nyimbo.db` are reused.

| Script | Does |
|---|---|
| `npm run dev` | Builds the content databases, then runs `server.ts` (Express + Vite middleware) on :3000 |
| `npm run build` | Content databases → Vite build → bundles `server.ts` to `dist/server.cjs` |
| `npm run start` | Runs the production bundle |
| `npm run lint` | `tsc --noEmit` |

## Offline scripture and hymns

`bible.db` (~2 MB) and `nyimbo.db` ship with the app and are opened in the
browser with **sql.js**, so reading, searching and the verse of the day never
touch the network.

[`src/lib/db.ts`](src/lib/db.ts) starts downloading both files at module import,
before React mounts, and reports progress to the splash screen. It uses the
pure-ASM.js build of sql.js (no WebAssembly) and a non-streaming fetch on
Capacitor, both to avoid WebView stalls. Each file's SQLite magic header is
verified after download, so a 404 page served in place of a database fails with
a clear message instead of a parser crash.

The databases are generated by [`build_clean_bible.ts`](build_clean_bible.ts)
and [`build_clean_nyimbo.ts`](build_clean_nyimbo.ts), which run as part of both
`dev` and `build`.

## Two data paths

Anything touching church data can travel two ways, decided at runtime by
[`src/lib/supabaseClient.ts`](src/lib/supabaseClient.ts):

1. **Direct** — if a Supabase URL and anon key are configured, the browser talks
   to Supabase itself and the Express API is bypassed. This is the path the
   Android build uses.
2. **Via the API** — otherwise, requests go to `${BACKEND_URL}/api/...` and
   [`server.ts`](server.ts) talks to Supabase.

Both paths are implemented for login, registration, reading contributions, and
completing a profile. Changes to one need mirroring in the other.

## API authentication

The `/api/member/*` endpoints identify the caller **only** from a bearer token
that Supabase has verified. They ignore any email supplied by the client.

`/api/auth/login` and `/api/auth/register` return an `access_token`; the client
stores it and [`fetchWithCache`](src/lib/fetchWithCache.ts) attaches it to every
subsequent request. Server-side, each request runs through a Supabase client
bound to that token, so row-level security applies exactly as it would in the
browser.

**`SUPABASE_ANON_KEY` must be set for this to work.** A service-role key
bypasses row-level security and must never be used to serve a member request.

## How giving is read

`contributions.type` only holds `Zaka` or `Sadaka`. The Pastor app records every
other category — Majengo, Makambi, custom labels — as `type: 'Sadaka'` with the
real label in `payment_method`.

[`src/lib/contributions.ts`](src/lib/contributions.ts) resolves this, and is
imported by both the browser and `server.ts` so the two cannot drift. Reading
`type` directly reports a member's Majengo gift to them as Sadaka.

Totals are always recomputed from the stored rows rather than trusted from a
cached response, so a stale server payload cannot survive a change to the
aggregation rules.

## Member self-service

A member may fill in `phone`, `marital_status`, `gender` and `residence` — but
only where the church left them blank. Existing values are never overwritten.
Enforced in both data paths, and in the database by the
`guard_congregant_self_update` trigger once
[`../database/rls_policies.sql`](../database/rls_policies.sql) is applied.

Registration requires the address to already exist in `congregants`. Members
cannot self-onboard; a pastor or treasurer enrols them first.

## Design tokens and accessibility

The palette was authored against dark navy, where the golds score 7.5–11:1. On
the light theme — which is the **default** — the same golds landed at 1.99:1,
making verse numbers and section labels effectively invisible. Three tokens in
[`src/index.css`](src/index.css) fix that, and new work should use them rather
than raw hex:

| Token | Use | Light | Dark |
|---|---|---|---|
| `--gold-ink` | gold as **text** on a surface | `#7d5410` | `#d9a020` |
| `--gold-fill` | gold as a **background** | `#d9a020` | `#d9a020` |
| `--on-gold` | anything sitting **on** a gold fill | `#1F1503` | `#1F1503` |
| `--muted-ink` | secondary text | `#64748b` | `#94a3b8` |

`--on-gold` deliberately does **not** follow the theme, because the surface it
sits on does not either: the gold fill is identical in both themes, so its label
must be too. White on gold is 2.33:1; this is 7.71:1.

Every panel now follows the theme, including the member card and the Historia
year summary — both were previously dark navy in *both* themes, which made them
read as foreign slabs on the light cream page. Because they now flip, style them
with ordinary `dark:` variants and the tokens above.

Rules worth keeping:

- **11px is the type floor.** The UI previously used 7px, 8px and 9px in 106
  places. Inputs stay at 16px or iOS Safari zooms the page on focus.
- **Interactive controls need ≥24px** (WCAG 2.5.8), and 44px where it is cheap.
- **Icon-only buttons need `aria-label`.** There were none in the whole file.

Verified with a live DOM audit across all three tabs in both themes: zero
contrast failures, zero controls under 24px. A handful of controls sit between
24px and 44px — conformant, but worth enlarging if you touch them.

**Fonts are still fetched from Google Fonts.** In an app built to work offline
this means the typography silently falls back whenever the network is absent.
The import has been trimmed to the weights actually used, but self-hosting the
five families is the real fix.

## Layout

```
src/
├── App.tsx                 the whole UI (three tabs)
├── main.tsx
├── types.ts
└── lib/
    ├── db.ts               sql.js loader + Bible/hymn queries
    ├── supabaseClient.ts   direct-connection client
    ├── contributions.ts    category resolution + totals (shared with server.ts)
    └── fetchWithCache.ts   backend URL, token, offline HTTP cache
server.ts                   Express: content API + member API + Vite/static
api/index.ts                Vercel entry point (re-exports server.ts)
public/                     bible.db, nyimbo.db, sql-wasm.wasm
android/                    Capacitor project
```

`_archive/` holds files that are no longer part of the build; see its README.
